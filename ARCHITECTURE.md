# Rikugan Platform — Architecture Map

A token-cheap reference for working on this repo. Read this instead of re-discovering structure/conventions by grepping the whole tree on every task. Keep it updated when you add a new router, model, established pattern, or top-level page — a stale map costs more tokens than none.

## Stack

Backend: FastAPI + SQLModel + PostgreSQL + Celery/Redis, Python 3.12 (pinned — 3.9 too old, 3.14 breaks `pydantic-core`/`psycopg` wheels).
Frontend: Next.js 16 (App Router) + TypeScript + Tailwind, dark-theme "Rikugan" design system.
Deployment: `docker-compose.yml` at repo root (postgres, redis, backend, celery-worker, frontend) — see `README.md` Quickstart.
Migrations: Alembic (`backend/alembic/`) — `init_db()` in `backend/app/core/db.py` runs `alembic upgrade head` on startup, not `create_all()`. **Any model change needs a real migration** (`alembic revision --autogenerate`, then hand-check it).

## Directory map

```
backend/app/
  api/        one file per resource, FastAPI router — see table below
  core/       shared logic: db engine, crypto, scoring, dedup, scanners' HTTP clients, Celery app
  models/     models.py — single file, every SQLModel table + enum (see Models below)
  scanners/   runner.py (subprocess dispatch), discovery.py (regex route extraction), parsers.py (tool output → Finding dicts)
  tasks/      Celery tasks — scan/discovery/sbom/pr_guardrail all run async via .delay()
backend/alembic/versions/   one file per migration, ordered by down_revision chain
backend/tests/    pytest, TestClient + sqlite in-memory (see Testing below)

frontend/src/app/(dashboard)/   one directory per sidebar page (route-mapped)
frontend/src/components/        shared non-page components (see Frontend components below)
frontend/src/components/ui/     shadcn-style primitives (Button, Card, Badge, Input, Label, Skeleton...)
frontend/src/lib/api.ts         single API client — every backend call + response type lives here
frontend/src/lib/poll.ts        shared polling helper for async job status (scan/discovery/sbom runs)
```

## Backend routers (`backend/app/api/*.py`)

| Router | Mount | Auth | Covers |
|---|---|---|---|
| `auth` | `/api/auth` | — | login/logout/me, session cookie issuance |
| `workspaces` | `/api/workspaces` | login (bootstrap: admin) | org/workspace creation, API key |
| `admin_workspace_roles` | `/api/admin/workspace-roles` | admin | assign `WorkspaceMembership` |
| `targets` | `/api/targets` | login, workspace-scoped reads | repo CRUD, pipeline integration (`/{id}/pipeline-workflow` generate, `/{id}/pipeline-integrate` opens a real PR, #66; `POST /bulk-pipeline-integrate` + `GET /bulk-pipeline-integrate/{batch_id}` multi-select async batch wrapper, #68) |
| `findings` | `/api/findings` | login, workspace-scoped reads | list/triage/history/bulk-triage/no-AI enrichment (`/{id}/enrichment`, #71); list/get responses also carry resolved `sla_days`/`sla_violated` (#70) |
| `sla_rules` | `/api/sla-rules` | login, SECURITY_ENGINEER-or-admin writes | `SlaRule` CRUD -- workspace-scoped days-to-fix per severity, optionally scoped to a repo Group (#70) |
| `scans` | `/api/scans` | login, workspace-scoped reads | trigger scan (async via Celery), poll status (`GET /{id}` carries `elapsed_seconds`/`eta_seconds`), `GET /active` lists every running scan keyed by target (#212) |
| `discovery` | `/api/discovery` | login | API-route discovery (async), persisted + org-wide aggregate |
| `api_scan` | `/api/api-scan` | login, workspace-scoped | active API scan (nuclei, async via Celery) against a target's already-discovered endpoints; results land in the normal `Finding` table (`tool="api-scan"`) via the shared `Scan` row, not a bespoke schema (#72) |
| `sbom` | `/api/sbom` | login | SBOM generation (async), per-target + org-wide + export; `POST /{target_id}/malware-check` synchronous OSV malware re-check over existing inventory, gated by `require_workspace_role(DEVELOPER)` (#181) |
| `pr_guardrail` | `/api/pr-guardrail` | login | diff scan, ignore/approval workflow |
| `github` / `github_app` | `/api/github*` | login (some public for GH callbacks) | activity, App manifest flow, multi-install |
| `webhooks` | `/api/webhooks` | HMAC signature, not session | GitHub webhook deliveries |
| `ai` | `/api/ai` | login | remediation analysis — Anthropic or OpenAI-compatible provider |
| `config` | `/api/config` | admin | `PlatformConfig` (AI provider, keys, Slack webhook, Jira config — encrypted); `POST /test-slack`/`POST /test-jira` make real outbound calls to verify credentials (#74) |
| `reports` | `/api/reports` | login | compliance posture export (CSV/PDF) |
| `admin` | `/api/admin` | admin | user CRUD |
| `policies` | `/api/policies` | admin | policy-as-code rules |
| `tools` | `/api/tools` | login; install routes admin-only | scanner health check, marketplace registry, per-workspace usage assignment, one-click install (`POST /{tool}/install` + `GET /installs/{id}`, #216) |
| `audit` | `/api/audit` | login | audit log |
| `search` | `/api/search` | login | global search |
| `ingest` | `/api/ingest` | Workspace API key (not session) | external CI/CD push |

Registration pattern in `backend/app/main.py`: `login_required`/`admin_required` are `Depends(...)` lists applied per-router via `app.include_router(x.router, dependencies=...)`, not per-route. Look there first when adding a new router.

## Models (`backend/app/models/models.py`)

Single file, ~380 lines, every table + enum. Key relationships:
- `Organization` → `Workspace` → `Target` (a scanned repo) → `Finding`/`Scan`/`ApiEndpoint`/`SbomComponent`
- `User` has a **global** `UserRole` (admin/user/viewer/developer/security_engineer) — admins bypass all workspace scoping
- `WorkspaceMembership` (user_id, workspace_id, `WorkspaceRole`) — **workspace-scoped** role, layered on top of the global role, added in #32. Non-admin visibility on GET/list endpoints is filtered by this (via `accessible_workspace_ids()` in `backend/app/api/auth.py`, added in #57)
- `PRGuardrailScan` → `PRGuardrailFinding` (net-new-only findings from a diff scan, separate from the main `Finding` table so PR-branch noise doesn't pollute default-branch posture)
- `DiscoveryRun`/`SbomRun` — async job tracking rows (status/error/count), added in #59 when scan/discovery/sbom moved off the request thread onto Celery
- `PipelineIntegrationBatch` → `PipelineIntegrationBatchItem` — same async-job-tracking shape as `DiscoveryRun`/`SbomRun`, for #68's bulk "Add Pipeline" (multi-select wrapper around #66's per-target mechanism); one item per selected target, each with its own succeeded/failed/already_integrated outcome so one target's GitHub error doesn't sink the batch
- `GitHubAppConfig` (potentially multiple, one per App) → `GitHubInstallation` (FK to the App that minted it) — multi-App/multi-install support added in #34, this used to be assumed single-row
- `NotificationEventType` gained a `MALICIOUS_PACKAGE` member (#179) — dispatched by ingestion when `finding.tool == "osv-malware"` (see the OSV malicious-package pattern below); the new enum value is a manual `op.execute` migration because autogenerate does not detect added enum members

## Established patterns (read before reinventing)

- **Workspace-scoped reads**: `accessible_workspace_ids(session, user)` in `backend/app/api/auth.py` — returns `None` for admins (no filter), else the caller's `WorkspaceMembership` workspace ids. Apply to every new GET/list endpoint that returns workspace-owned resources.
- **Secrets at rest**: `encrypt_secret()`/`decrypt_secret()` in `backend/app/core/crypto.py` (Fernet, key from `PLATFORM_ENCRYPTION_KEY`). Used for GitHub App secrets and the OpenAI-compatible provider key. Note: `PlatformConfig.anthropic_api_key` is a pre-existing plaintext exception, left alone — don't copy that, encrypt new secret fields.
- **Async long-running work**: don't run `git clone` + scanner subprocess synchronously in a request handler. Dispatch a Celery task (see `backend/app/tasks/`), create a tracking row (`Scan`/`DiscoveryRun`/`SbomRun`) with `status="running"`, return 202 immediately, poll via a GET endpoint. Frontend uses `frontend/src/lib/poll.ts`.
- **git clone safety**: `clone_repo()` in `backend/app/scanners/runner.py` validates `repo_url` (https + github.com host only), uses `--` before the positional URL arg, and delivers the GitHub token via `http.extraHeader` env vars — never embed a token in a URL or pass one where a `CalledProcessError` could leak it into a response.
- **"All repos" dropdown option**: `TargetPicker`'s `allowAll` prop + `ALL_TARGETS` sentinel (`frontend/src/components/target-picker.tsx`) — one dropdown with a 0-value "All repositories" entry, not a separate tab/toggle. Established for SBOM, reused for reports.
- **Persisted-scan pattern**: `POST` triggers a real (now async) scan and upserts results; `GET` reads persisted state without re-scanning. Net-new items get an `is_new`/`first_seen`/`last_seen` treatment (see `upsert_endpoints()`/`upsert_components()` — extracted to `backend/app/core/discovery_ingestion.py`/`sbom_ingestion.py` to avoid an api↔tasks import cycle).
- **Dedup**: `compute_dedup_hash()` in `backend/app/core/dedup.py` — fingerprints on `(rule_id, file_path, tool, normalized_snippet)`, survives line-shift refactors. `file_path` must be normalized (relative to repo root, not the scan-scoped clone dir) via `normalize_file_path()` in `runner.py` before hashing, or dedup silently breaks.
- **Priority scoring**: `backend/app/core/scoring.py` — `severity_weight × criticality_weight × 40`, boosted by real-time EPSS (`core/epss.py`) and CISA KEV (`core/kev.py`, cached 1hr) lookups.
- **No-AI finding enrichment** (#71): `core/nvd.py`/`core/osv.py` fetch real CVE description/CVSS/CWE (NVD) and known fixed versions (OSV.dev, queried directly by CVE ID via `/v1/vulns/{cve_id}`, which resolves CVE as an alias) — both free, no API key. `core/cve_enrichment.py` caches the result **forever** in the `CveEnrichment` DB table (unlike EPSS/KEV's short in-process TTL cache above — a single CVE's data is effectively immutable, so this is a real forever-cache, not a refresh-on-interval one). Exposed via `GET /api/findings/{id}/enrichment`; returns null fields for findings with no `cve_id` (SAST/secrets findings) rather than fabricating a CWE/CVSS. Deliberately separate from the AI Analysis feature (`api/ai.py`) — works with zero AI provider configured.
- **Downloadable exports**: `Content-Disposition: attachment` header pattern, see `sbom.py`'s `/export`/`org/export` and `reports.py` — frontend downloads via `fetch(..., {credentials:"include"})` → blob → `URL.createObjectURL` → synthetic `<a>` click (see `exportSbom`/`exportOrgSbom` in `frontend/src/lib/api.ts`).
- **Admin page tabs**: `frontend/src/app/(dashboard)/admin/page.tsx` — a `TABS` array + one component file per tab in the same directory (`user-management.tsx`, `workspace-roles.tsx`, `groups.tsx`, `sla-rules.tsx`, `global-integrations.tsx`, `tools-health.tsx`, `policies.tsx`, `approval-queue.tsx`). Add a new tab by adding one entry + one file, not by editing the others.
- **A router grown large enough to cover unrelated concerns becomes a package, not a longer file** (#223): `backend/app/api/tools/` — `health.py` (`GET /health`), `registry.py` (`GET /registry`), `assignments.py` (`GET`/`PUT /assignments`), `install.py` (`POST /{tool}/install` + `GET /installs/{id}`), aggregated by `__init__.py`, which builds the `/api/tools`-prefixed router and mounts each submodule onto it with `tags=["tools"]` applied once at the aggregation point. The only cross-module dependency is `registry.py` importing `health.py`'s `_check_one` (same subprocess `--version` probe, different tool set) — there was no real coupling being expressed by the original single file, only convenience at the time each concern was added. `app.main`'s `from app.api import tools; app.include_router(tools.router, ...)` is unchanged either way, since Python does not distinguish a module from a package at the import-statement call site.
- **Two ways to scan a PR, and server-side is the default** (#245). This is the single thing people get wrong when they arrive: PR Guardrail and Pipeline Integration are separate mechanisms, not two halves of one.
  - **Server-side (default).** `POST /api/webhooks/github` verifies the HMAC against the App's webhook secret, filters `pull_request` to `{opened, reopened, synchronize}`, resolves the `Target` by `clone_url`, and dispatches `run_pr_guardrail_scan_task.delay(target_id, pr_number)`. The worker clones, runs the target's configured tools, diffs to net-new, posts the comment and sets the commit status. Setup is: install the GitHub App, register the target. **No Actions minutes, no secrets in the customer's repo, no committed workflow file, and scanner versions upgrade once centrally** rather than drifting across N generated files.
  - **Actions-based (`pipeline_workflow.py`, below).** Generates `.github/workflows/rikugan-scan.yml` into the customer's repo; scanners run in their runner and push SARIF back. Costs their Actions budget on every PR and needs two repo secrets configured by someone with admin rights.
  - **When the Actions path is the right one:** the generated workflow reports into the job summary and artifacts **whether or not the ingest step succeeds**, so it degrades to a standalone `self-scan.yml`. That covers the case where Rikugan is not reachable from GitHub at all — which the webhook path cannot do, since it depends on GitHub reaching us. That is its niche; it is not a redundant second implementation.
  - Enabling **both** for one target double-scans every PR. Nothing prevents it today.
- **CI/CD pipeline integration** (#66): `backend/app/core/pipeline_workflow.py` generates a per-target GitHub Actions YAML that runs Semgrep/Gitleaks/Trivy (+ gosec for Go, detected from `Finding.tool` scan history or, failing that, GitHub's `/repos/{slug}/languages` API) natively in the runner and pushes SARIF back via `POST /api/ingest/{target_id}` — mirrors the dogfooding scan's own job structure (that scan now lives in `.circleci/config.yml`, moved off GitHub Actions when this repo's Actions minutes ran out; the *generated* workflow is still GitHub Actions YAML, since it targets the customer's repo, not this one) since GitHub's cloud runners can't reach a `localhost` backend either; the generated workflow requires `RIKUGAN_API_URL`/`RIKUGAN_API_KEY` repo secrets pointing at a publicly reachable Rikugan deployment. `backend/app/core/pipeline_pr.py` opens a real PR adding it via the GitHub App installation token (branch + contents-API file write + PR, same token-minting as PR Guardrail's `set_commit_status`). **GitHub gates writes under `.github/workflows/` behind a separate `workflows` App permission**, distinct from `contents` — confirmed live via a 403 "Resource not accessible by integration" even with `contents: write` granted; `github_app.py:build_manifest` declares `workflows: write` for this, but an App installed before this existed needs its owner to re-approve updated permissions in GitHub's UI (not automatable).
- **Bulk async job with per-item outcomes** (#68): `POST /api/targets/bulk-pipeline-integrate` accepts a list of `target_ids`, drops any the caller can't access or hold at least `DEVELOPER` on (per-target, since a selection can span workspaces), creates a `PipelineIntegrationBatch` + one `PipelineIntegrationBatchItem` per eligible target, and dispatches `app.tasks.pipeline_tasks.run_pipeline_integration_batch` via `.delay()` (#59-style: real GitHub API calls per item, so this must not block the request thread). The task processes items **sequentially** with a small fixed delay between them (`INTER_ITEM_DELAY_SECONDS`) rather than firing them concurrently, to stay polite to GitHub's rate limits — real rate-limit-aware concurrency (parsing `X-RateLimit-Remaining`) is future work, not needed for a first version. Targets already `Target.pipeline_integrated` are skipped and reported `already_integrated`, not re-run or treated as a failure. `frontend/src/app/(dashboard)/targets/targets-list.tsx` follows `findings-list.tsx`'s checkbox + bulk-action-bar pattern, then polls `GET .../bulk-pipeline-integrate/{batch_id}` via `frontend/src/lib/poll.ts`'s `pollUntilSettled` to show live per-repo status.
- **Most-specific-wins settings inheritance** (#62, PR Guardrail enforcement mode): `Target.enforcement_mode` / `Group.enforcement_mode` / `Workspace.enforcement_mode` are all nullable `str` columns (`None` = "no override here, inherit"), resolved by `app.core.enforcement.resolve_enforcement_mode(session, target)`: target's own value wins if set; else its group(s)' value (a target with multiple groups that disagree resolves to the **most restrictive** — block > alert > disabled, fail-closed rather than "first/last group wins"); else the workspace's value; else the hardcoded default `"block"`. `resolve_enforcement_mode_with_source` additionally returns which level ("target"/"group"/"workspace"/"default") the effective value came from, for UI legibility (`GET /api/targets/{id}` embeds `effective_enforcement_mode`/`enforcement_mode_source`). This is a distinct concept from `app.core.policy` (Sprint 4): policy decides *which* findings are severe enough to count as blocking; enforcement_mode decides whether a PR carrying blocking findings actually fails the build (`block`), just warns via a non-blocking commit status (`alert`), or PR Guardrail doesn't run at all (`disabled`) — wired into `app.core.pr_guardrail_executor.execute_pr_guardrail_scan` at the very top (disabled short-circuits before any clone/scan/comment/status) and again just before `set_commit_status` (alert still posts the PR comment but sends GitHub `success` with a description noting it's non-blocking, since GitHub commit statuses have no dedicated "neutral" state).

- **SLA resolution + query-time violation** (#70): unlike #62's single inherited scalar, an SLA is a matrix -- `SlaRule` rows keyed by `(workspace_id, group_id | null, severity)` with a `days_to_fix` int, since Critical and Low need very different windows even within the same group. `app.core.sla.resolve_sla_days_with_source(session, finding)` resolves: a group the finding's target belongs to has a rule for this severity (most-restrictive/fewest-days wins on multi-group conflict, same fail-closed philosophy as #62) -> else the workspace's null-`group_id` default rule for this severity -> else `None` (no SLA shown, never a fabricated number; there's deliberately no per-target override in this first version, unlike enforcement_mode's 3-level chain). `compute_sla_status` additionally applies violation logic on read (no background job): a finding past its SLA window is only "in violation" while still open (state not in Mitigated/Accepted Risk/False Positive/Won't Fix -- Reopened still counts as open). `GET /api/findings` and `/{id}` embed `sla_days`/`sla_violated`; `GET /api/dashboard/sla-compliance` aggregates workspace-wide.
- **Configurable dashboard / widget catalog** (#69): `app.core.widgets.WIDGET_CATALOG` is a small, concrete set of real widgets (kpi_cards, findings_trend, cve_timeline, sla_compliance, top_risky_repos, recent_findings, security_score), each `{name, description, resolver, default_config}` -- deliberately not a generic "arbitrary chart config" system. Add a new widget type by adding one catalog entry + one `resolve_*` function, same "one entry + one file" extensibility as the admin page tabs. `DashboardLayout` (one row per user, `widgets` JSON column: ordered `[{id, widget_id, config}]`) is the saved composition; `GET /api/dashboard/layout` falls back to `build_default_layout()` (deterministic `default-<widget_id>` instance ids, not random, so an unsaved user's `/layout` and `/widget-data` responses key-match) when no row exists yet. `GET /api/dashboard/widget-data` batches every widget's real data in one round-trip, isolating one widget instance's resolver failure from the rest (`{"error": ...}` for just that entry). Frontend: `frontend/src/components/dashboard/dashboard-board.tsx` (edit mode, add/remove/move-up-down reorder -- plain buttons, not a drag library) + `widgets.tsx` (one render component per widget type, dispatched via `WidgetBody`).
- **Composite security health score** (#63): `app.core.security_score.compute_security_score(session, target_ids)` combines 5 real components into a 0-100 score + A-F letter grade -- open findings weighted by `SEVERITY_WEIGHT` (normalized per in-scope target), SLA compliance (reuses #70's `compute_sla_status` verbatim, neutral 100 when zero findings have an applicable rule), scan coverage (% of targets with a `Scan` row in the last 30 days), FP rate (findings currently `FALSE_POSITIVE` / all findings ever, all-time), and a week-over-week trend reconstructed from the real `FindingStateLog` audit trail (not a guess). All constants/weights/windows are documented in that module's docstring. `resolve_target_ids_for_scope` (same file) is the shared org/group/target scoping helper -- mutually-exclusive `target_id`/`group_id`, same convention as #61's `findings.py`, used by both `GET /api/dashboard/security-score` (standalone) and the `security_score` dashboard widget (#69) so the two always agree for the same scope. The widget's own saved instance has no scope config (there's no per-widget config editor in #69's dashboard yet) -- its frontend component (`SecurityScoreWidget` in `widgets.tsx`) self-fetches the target/group picker lists and calls the standalone endpoint directly for a scoped drill-down, client-side.

- **Active API scanning** (#72): builds on Sprint 1's static API Discovery (`ApiEndpoint`, `app/scanners/discovery.py`) by actually probing the routes it found. `Target.api_base_url` (nullable, operator-set via `PATCH /api/targets/{id}`) is the *only* source of a scan host -- `app.core.api_scan_targets.build_scan_urls(session, target, endpoint_ids)` joins it with each persisted `ApiEndpoint.route`, rejecting (and dropping, not failing the whole scan) any route that would resolve outside that host's own netloc, so a caller can never point an active scan at an arbitrary third-party URL, only at endpoints this platform already discovered for a target its owner already configured. `runner.run_nuclei(urls)` shells nuclei out via a `-l <tempfile>` URL list (never argv/shell-joined), defaults to excluding `dos,fuzz,intrusive` template tags (`settings.nuclei_exclude_tags`) so a first run is passive/safe, and bounds both nuclei's own `-rate-limit`/`-timeout` and the subprocess call itself (`subprocess.run(timeout=settings.nuclei_timeout_seconds)`). `app.tasks.api_scan_tasks.run_api_scan` (dispatched by `POST /api/api-scan/{target_id}`, same create-tracking-row-then-`.delay()` shape as #59) runs nuclei and pipes its `-jsonl` output through `parsers.parse_nuclei` into the **existing** `ingest_findings()` path -- deliberately no separate `ApiScanFinding` table; results are ordinary `Finding` rows tagged `tool="api-scan"`, so dedup/priority-scoring/SLA/Jira-auto-create/notifications all apply unmodified, and `GET /api/api-scan/{target_id}/latest` reads the shared `Scan` table (`Scan.tool == "api-scan"`) rather than a bespoke run-tracking model.

- **Scan progress + grounded ETA** (#212): `Scan.status`/`started_at`/`completed_at`/`error` already existed; what was missing was anything surfacing them. `backend/app/core/scan_eta.py` estimates a run's duration as the **median of that target's last `MAX_SAMPLES` completed runs of that same tool**, and returns `None` below `MIN_SAMPLES` — a global average or a fixed "about 30 seconds" was rejected deliberately, because scan duration is dominated by repo size and an estimate that is routinely wrong costs more trust than no estimate. Only `completed` runs are sampled: a failed run's duration measures how long the platform took to give up (usually a clone timeout), not how long the work takes. `GET /api/scans/{id}` and `GET /api/scans/active` both carry `elapsed_seconds` (always) and `eta_seconds` (nullable); the frontend renders a countdown only when the latter is non-null and falls back to `running for 45s` otherwise. `/active` also sweeps stale rows via `mark_stale_if_needed` before reporting, since it backs list views and is often the first read to touch a row a dead worker left `running` — reporting those as active would paint a permanent in-flight badge on Targets. Because active API scanning (#72) writes to the same `Scan` table with `tool="api-scan"`, DAST gets this for free rather than needing a parallel surface. Frontend: `components/scan-status.tsx` (one shared badge/progress line — four phases, `queued` kept distinct from `running` because the dispatch-to-worker gap is real), `hooks/use-scan-run.ts` (follows one dispatched scan; elapsed ticks locally anchored to the *server's* count, not the client clock, so clock skew cannot leak into the display), and `hooks/use-active-scans.ts` (adaptive poll — frequent while anything runs, backed off hard when idle).

- **One-click tool install** (#216): the marketplace can install a scanner into the running backend, which #75 originally declined to build because installing software from a web request is an RCE surface. What makes it defensible is that **the API takes a registry key, never a package name**: `POST /api/tools/{tool}/install` looks `tool` up in `TOOL_REGISTRY` and 400s anything absent, so the installable set is fixed at deploy time in source and there is no path from a request body to a package. The command is an argv list built from a module constant (`[sys.executable, "-m", "pip", "install", ...]`) with the package as one element — no shell, no interpolation, no `shell=True`, same rule as `runner.clone_repo`. Admin-only, rate-limited, and the `ToolInstallRun` row doubles as the audit record (there is no generic audit table; the audit feed is derived from `FindingStateLog`/`Scan`). Only tools with a `pip_package` get a button — gitleaks/trivy/gosec/tfsec/kics need brew/go/docker, which the image does not carry, so they keep the copyable `install_cmd` rather than offering a button that cannot work. An install is only reported successful once the tool's own `version_cmd` answers: pip exiting zero is not proof the binary runs, which is exactly the setuptools/`pkg_resources` failure shape. **Installs are ephemeral** — they land in the running container and a redeploy reverts them; the UI says so, because an operator who believes a scanner is installed when it is not gets silent zero-finding scans.
- **Image build coverage** (#215): `.github/workflows/docker-build.yml` builds all three images post-merge, on PRs touching build inputs, and weekly — the cron is what catches a transitive dependency resolving differently under an unchanged `requirements.txt`, which is how a broken image reached main with every other check green. Caching is off deliberately. `backend/scripts/verify_tools.py` then runs each `BUNDLED_TOOLS` entry's `version_cmd` **inside the built image**, because a successful build only proves the install commands exited zero, not that the binaries still run — and a broken scanner produces zero findings that read exactly like a clean repo.

- **Slack/Jira integration + auto-ticket-creation** (#74): `PlatformConfig` gained `slack_webhook_url` (encrypted) and `jira_url`/`jira_api_token` (encrypted)/`jira_project_key`/`jira_issue_type`/`jira_auto_create_severity`, same never-echo-raw-secret / `*_set: bool` pattern as #67's `openai_compatible_*` fields. `backend/app/core/slack_integration.py`/`jira_integration.py` hold the real outbound-HTTP logic (Slack incoming-webhook POST, Jira REST v2 `myself`/`issue` calls via Bearer-token auth) used both by `POST /api/config/test-slack`/`test-jira` (admin "Test Connection" buttons) and by ticket creation. Auto-create is a single severity threshold (`jira_auto_create_severity`, nullable, e.g. "Critical" = auto-create at Critical or above) checked in `app.core.ingestion.ingest_findings` after each net-new `Finding` is committed (best-effort -- a Jira outage is logged, not raised, so it never fails a scan). Deliberately a single scalar rather than a rule table for this first version, unlike `PolicyRule`/`SlaRule` -- a natural next step if per-severity/per-group criteria are needed later.

- **OSV malicious-package detection, tracking & blocking** (#180/#181/#179): `backend/app/core/osv_malware.py` is a pure (no-DB) OSV.dev malicious-package client — `check_packages_for_malware(packages) -> dict[(name,version), MaliciousPackage] | None` returns **`None` on check failure** (network/timeout/non-200, non-list or length-mismatched `results`, or a paginated `next_page_token` — all fail closed so a short/partial response can never read as "clean") and an empty dict only when the check completed and nothing was malicious (`ECOSYSTEM_BY_PACKAGE_TYPE` maps npm/pip/gomod; `CHUNK_SIZE=250`; `OSV_MALICIOUS_ID_PREFIX="MAL-"`). `backend/app/core/osv_malware_ingestion.run_malware_check` reads the target's default-branch `SbomComponent` rows and `ingest_malicious_packages` persists hits as **ordinary `Finding` rows** (`tool="osv-malware"`, `severity=Critical`, `rule_id`=OSV id) deduped via the existing `compute_dedup_hash` (file_path encodes `name@version` so dedup naturally covers package+version+osv-id) — no bespoke table, so PR blocking, Jira auto-create (`_maybe_auto_create_jira_ticket`), SIEM export (`_maybe_export_to_siem`), and notifications all fire for free through the same shared `app/core/ingestion.py` hooks as every other finding; `_maybe_notify_new_finding` dispatches a distinct `MALICIOUS_PACKAGE` event (#179) so users can opt into malicious-package paging without every Critical SAST finding. `sbom_tasks` runs `check_and_ingest_malware` best-effort after SBOM upsert (logged, never fails the SBOM run); `POST /api/sbom/{target_id}/malware-check` is a synchronous re-check over existing inventory (no SBOM regen) returning `{"status": "clean"|"found"|"failed", ...}`. Open/Reopened findings whose package left the malicious set are mitigated only when the check completed, never when it failed (stale sweep filters on `OPEN_STATES` from `app/core/security_score`, not just `OPEN`). The `NotificationEventType.MALICIOUS_PACKAGE` enum member is a manual `ALTER TYPE ... ADD VALUE IF NOT EXISTS` via `op.execute` in the migration (`backend/alembic/versions/8f2d3a1b4c5e_add_malicious_package_notification_179.py`) because Alembic autogenerate does not detect new enum values.

- **GitHub dependency-graph SBOM ingestion** (#227): `backend/app/core/github_dependency_graph.py`'s `fetch_dependency_graph(repo_url, token) -> list[dict]` fetches `GET /repos/{owner}/{repo}/dependency-graph/sbom` (SPDX JSON) and `parse_spdx_packages` normalises it to the `{name, version, package_type, purl}` shape `sbom_ingestion.upsert_components` consumes — raising `DependencyGraphUnavailable` rather than returning `[]`/`None` on any failure, since "GitHub said there is nothing" and "we could not ask" are different facts and only the first is evidence of a clean repo. `sbom_tasks.run_sbom_generation` clones the target's default branch (for the AIBOM extraction, #190), imports the dependency graph as its dependency inventory, and persists it into the `SbomComponent` table via `sbom_ingestion.upsert_components(..., source="github")`, which tracks multi-source provenance per component (`source` becomes `"github,upload"` on a collision, via `_merge_sources` — a union, not a last-writer-wins overwrite) rather than deduping into a single winner. Trivy no longer generates the SBOM: its `trivy`/`trivy-license` modes remain findings scanners (CVE/OSS + license) and are unchanged. Token resolution goes through `github_token.resolve_github_token(session, workspace_id, slug)` (an admin-managed, encrypted-at-rest per-workspace PAT with TTL auto-purge, falling back to the GitHub App installation token) — see the GitHub token entry below. Two standalone, user-triggered import routes live in `backend/app/api/sbom.py` alongside Generate SBOM: `POST /{target_id}/github-sync` (imports just the dependency graph synchronously via the same `fetch_dependency_graph`, `502` when it's unavailable) and `POST /{target_id}/upload` (multipart upload of a CycloneDX/SPDX JSON document parsed by `parsers.parse_sbom_upload` — SPDX reuses `parse_spdx_packages` so an uploaded GitHub SBOM parses identically to one fetched automatically; capped at `MAX_SBOM_UPLOAD_BYTES` (25MB, `413` over), the first size cap on any request body in this codebase since it's also the first multipart-upload endpoint; `400` on invalid JSON or no parseable components) — both merge via `upsert_components`, then run the OSV malicious-package check (`check_and_ingest_malware`, #181) **best-effort** over the freshly persisted inventory (a malware-check crash never fails the import/upload; its own `"failed"` status is never reported as clean), and return `{target_id, count, new_count, malware}` where `malware = {status: "clean"|"found"|"failed", malicious_count, findings_created}`.

- **Per-workspace GitHub token storage** (#227): `GitHubToken` (`backend/app/models/models.py`, migrated by `backend/alembic/versions/a7d4f2e9c1b6_add_github_token_227.py`) stores one encrypted PAT per workspace (`workspace_id` unique, save replaces). The plaintext is **never persisted or echoed** — `upsert_github_token` writes `token_ciphertext` via `crypto.encrypt_secret` (Fernet, `PLATFORM_ENCRYPTION_KEY`); the API returns only `{token_set, created_at, expires_at}` (never-echo, same `*_set` shape as `app/api/config.py`). TTL is set by the saver (`expires_at` = now + chosen hours; `None` = never) and purged **lazily** (matching the project's no-Celery-beat staleness pattern, #153): `resolve_github_token` deletes an expired row on read and `purge_expired_tokens` runs on the status GET, so a token is unusable the instant it lapses. `backend/app/core/github_token.py` `resolve_github_token(session, workspace_id, slug=None)` is the single token resolution point with precedence **workspace PAT → GitHub App installation token**; the env/`gh` `GITHUB_TOKEN` fallback (`get_github_token`) was **removed entirely** from every target-repo call site — `github_get(path, params, token)` now takes an explicit resolved token, and `clone_repo`/`detect_languages`/`github_dependency_graph`/PR-guardrail/org-activity call sites all thread `resolve_github_token(...)`. Admin-only routes in `backend/app/api/github_token.py` (`/api/github-token` GET/PUT/DELETE + `POST /test`, real `GET /user` check) drive the "GitHub Token" card in the Global Integrations admin page (fine-grained repo-scoped read-only PAT is recommended). Hard rule: token plaintext/ciphertext/`Authorization` header/request body are **never logged** — failures log only `workspace_id`/status/`slug`.

## Workflow notes for background agents working this repo

- Always `git fetch origin main` and branch from current `origin/main` HEAD before starting — this project has repeatedly hit bugs from stale-base agents.
- No Alembic before #58; if you're reading old context/history that mentions manual `ALTER TABLE`/`ALTER TYPE` against the live dev DB, that's no longer the right approach — write a real migration instead.
- If you do live-verification writes against the shared dev Postgres (creating real tables/rows to prove something works), say exactly what you created in your final report — merges have repeatedly needed to reconcile schema that existed on the DB but wasn't yet stamped in Alembic's `alembic_version`.
- Live-verify with real data wherever feasible (real clone, real scan, real HTTP calls) — "no mock data" is enforced throughout this project, including in how work gets verified, not just what ships.
